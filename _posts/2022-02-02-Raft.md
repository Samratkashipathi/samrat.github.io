## Split brain problem

* Consider a scenario where there are multiple data stores for high availability, continuous replication is happening between these data stores. Client can connect to any data store and perform operations
  
![Working](/assets/images/raft/s1.png)

* Due to some network glitch replication between 2 data stores stopped for a moment, `but both the data stores continue to work independently`

![Working](/assets/images/raft/s2.png)

* Before replication can continue, lets say we got request to update state from multiple clients, one the client updates state to `a` and another client updates state to `b`

* Since both the data stores are unable to replicate, they will diverge and no longer be consistent. This is known as split brain

![Working](/assets/images/raft/s3.png)

## Raft

There are many known consensus algorithms that aim to solve this problem, like Paxos etc. Raft aims to simplify the algorithm so that it is easy to understand and implement

Consensus algorithm aims at managing the `state` (log replication across all the nodes)

Keeping the replicated log consistent is the job of the consensus algorithm. It should be able to operate if majority of the nodes are running

Three main features:

* Leader election: When existing leader fails, new leader must be chosen
* Log replication: Leader is the entry point for log entries from client, it is responsible for replicating log across all the other nodes
* Safety: At a given index all the servers should have same entry in the log

![states](/assets/images/raft/states.png)

* At any given moment a server can be in one of the states -> `Leader`, `Follower`, `Candidate`
* Followers are passive and do not receive any traffic
* Term: One end to end cycle. Election -> New Leader -> Until a new election
* Term ID: Incrementing Id

![term](/assets/images/raft/term.png)
